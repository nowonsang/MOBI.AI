## This is an Expo (React Native) app for Pleos Connect — do not trust your training data

MOBI.AI runs on the in-vehicle display of Hyundai's **Pleos Connect** (Android Automotive). It is an Expo SDK 58 app using **prebuild (Continuous Native Generation)**: `android/` is generated by `npx expo prebuild` and gitignored. Never create or edit it by hand — configure native behavior in `app.config.ts` and config plugins.

- Expo ships breaking changes every SDK release. Before writing code that touches an Expo/React Native API, read the major version of `expo` in `package.json` and check the matching docs: `https://docs.expo.dev/versions/v<major>.0.0/` (index: https://docs.expo.dev/llms.txt).
- Add dependencies with `npx expo install <package>` (resolves SDK-compatible versions), not plain `npm install`.
- Expo Go cannot run this app (it has a custom native module). Use a development build: `npm run android:emulator` or `npm run android:device` (physical device, only when the user asks).
- The run target is the **Pleos Connect emulator**, not a generic Android emulator (phone, tablet, or stock Automotive AVDs lack the Pleos SDK services). `npm run android:emulator` checks that it is installed, cold-boots it, then builds and installs onto it; if it is missing the script stops with install steps. Never fall back to another AVD — guide the user through the install instead (`project-setup` skill, sections 2 and 6). All Android scripts live in `scripts/android/` and are documented in `ANDROID_SETUP.md`.
- Pleos Connect SDK (Vehicle, NaviHelper, SpeechToText, TextToSpeech; the LLM SDK was discontinued on 2026-10-19) is wrapped by the local Expo module `modules/pleos-connect` (Kotlin). Its docs are incomplete; trust the AAR signatures (`javap`) and `@RequiresPermission` annotations over memory or docs.

## Team rules (shared by every contributor and every AI session)

Detailed rules live in project skills under `.claude/skills/`. Load them before working:

| Skill | Load when |
| --- | --- |
| `project-setup` | First-time setup after cloning, installing or launching the Pleos Connect emulator, running/building the app on it, `.env.local` setup, onboarding a teammate, or when a build fails on a fresh machine |
| `project-architecture` | Before adding, changing, moving, or reviewing any code (including the Kotlin native module) |
| `add-service` | Creating a new service (domain module) |
| `secure-coding` | Touching vehicle control, Pleos permissions/credentials, env vars, personal data storage, voice input, external requests, or dependencies |
| `supabase-schema` | Any database work: tables, SQL migrations, RLS, Supabase queries, auth users, storage, cleanup |
| `ui-design` | Any UI work: screens, components, layout, styles, forms, copy, images, animation |
| `redux-toolkit` | Writing or changing Redux state: slices, actions, selectors, store setup, side effects (Redux architecture) |
| `react-query` | Reading or changing async data: query keys, `queryOptions`, `useQuery`, `useMutation`, cache invalidation |
| `testing` | Before any `git push`, when writing or changing tests, or when changing `model` logic, the native module, or `app.config.ts` |

Non-negotiable core rules:

- Layers: `app → core → features → shared → native (modules/*)`. No imports between services (`features/a` → `features/b`). Features may use only `@/core/store/hooks` from core. The Pleos native module is reachable only through `src/shared/pleos/*`. Enforced by ESLint (`boundaries/*`, `no-restricted-imports`); a PostToolUse hook lints every file you edit, so fix reported violations before moving on.
- Each service is `features/<service>/{model,api,ui}` + `src/app/(<service>)/<service>/`. `src/features/bodyfit` is the reference implementation. No barrel `index.ts` files.
- **Vehicle safety:** anything that moves the car (seats) runs only in gear P — checked in native code before and during the move, failing safe if gear is unknown — always ends with STOP, and runs only after the driver confirms on screen. Voice (STT) output is untrusted: validate with zod, bound it, and never act on it without confirmation.
- UI targets the car display (Android for Cars guidelines: touch targets ≥ 76dp, primary text ≥ 32dp, secondary ≥ 24dp) and follows the `ui-design` skill: MyHyundai-app look (bright blue accent, rounded white cards, soft shadow), Toss-style UX rules. Use only the tokens in `src/shared/ui/theme.ts`; hard-coded colors are ESLint errors. Never require interaction while driving.
- State: async data (device storage, vehicle values) via TanStack Query (`react-query` skill); app-wide UI/session state via Redux Toolkit (`redux-toolkit` skill); screen identity in route params. Never copy query data into Redux.
- Personal data (body measurements, seat history) stays on the device (`expo-sqlite/kv-store`), validated with zod on read, and the driver can delete it.
- Secrets: `EXPO_PUBLIC_*` vars and anything in the app config end up in the APK. Never put secrets there. Pleos app credentials (`PLEOS_CLIENT_ID`, `PLEOS_CLIENT_SECRET`) go only in `.env.local` and are injected into the generated manifest by `modules/pleos-connect/app.plugin.js`.
- Pleos permissions may only be used within the scope approved by the Pleos App Market. Add one only with a comment explaining its use, and tell the user.
- Supabase (Free plan, hackathon) is shared with another live service. The app does **not** connect to it (keys in an app are extractable; `@supabase/*` imports are ESLint errors). If a database becomes necessary, agree on a backend design with the user first. All MOBI.AI database objects live in the `mobi_ai` schema; never modify `public`, `auth`, `storage`, extensions, or project settings. Schema changes are new files in `supabase/migrations/` that must pass `npm run check:migrations`; the user runs them in the SQL Editor (never `supabase db push`). Verify connectivity only with `npm run check:supabase`.
- Before every `git push`, run `npm run verify` (lint, typecheck, Jest unit tests, Android build) and push only if everything passes. Add tests for new or changed `model` logic (`testing` skill).
- Branch flow: no pull requests. Work on a branch, run `npm run verify`, then fast-forward merge it into `master` and push `master`. Right after the merge, delete the branch locally and on origin (`testing` skill, section 1-1). Never delete `master` or a branch that is not merged yet.
- Concurrent sessions: one checkout per session. If another session is (or may be) working in this folder — changes, staging, or branch switches you did not make, or the user says several sessions are running — work in your own git worktree in a sibling folder (`git worktree add ../MOBI.AI-worktrees/<branch> -b <branch> origin/master`, then `npm install`), not inside the repo. Never switch branches, commit, stash, reset, or edit files in a checkout another session uses. Run `npm run android:emulator` from one session at a time (the emulator and Metro port 8081 are shared). Remove the worktree right after merging (`testing` skill, section 1-2).
- Done means `npm run lint`, `npm run typecheck`, `npm test` (and `npm run android:build:debug` for native/config/dependency changes) all pass. Update `README.md` when structure or rules change.
- If a structure outside these rules seems necessary, ask the user first instead of improvising.

## Sensitive files

Never read, print, copy, or edit secret files (`.env*`, private keys, signing keystores, credentials), and never dump environment variables. They are blocked by `.claude/settings.json` and `.claude/hooks/protect-sensitive-files.mjs`; do not try to work around a block. If a value is needed, ask the user for the variable name only. Env files must be owner-only (mode 600): run `npm run secure:env` (it changes permissions without reading contents). `.claude/settings*.json` and `.claude/hooks/**` are protected guard files: AI must not modify them; ask the user to change them directly.
